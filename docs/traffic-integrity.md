# Целостность трафика: кто и как считает байты

Документ отвечает на вопрос «может ли клиент обмануть сервер, скрыть скачки трафика
или подделать статистику», и фиксирует, откуда берётся каждая цифра в UI.

## 1. Короткий ответ

**Лимит тарифа и вся статистика считаются на сервере.** Ни Android, ни Windows,
ни сайт, ни расширение не могут увеличить или уменьшить свой расход:
они только читают уже посчитанные сервером значения.

Единственная лазейка, которая оставалась, — счётчики `Session.bytesRx/bytesTx`
(они видны в админке и в CLI). Их можно было прислать из клиента через
`POST /api/vpn/stats` и `POST /api/vpn/disconnect`. Лазейка закрыта:
байты принимаются только от доверенного репортера (нода / наш собственный
browser-proxy на loopback).

## 2. Откуда берутся цифры

| Что видит пользователь | Источник | Кто пишет данные |
|:--|:--|:--|
| «Лимит тарифа X из Y» (кружок/шкала на всех площадках) | `services/quota.ts → usedBytesInPeriod()` — `SUM(uploadBytes + downloadBytes)` по таблице `TrafficUsageBucket` за период | нода через `POST /api/node/...` |
| Графики и итоги в «Статистике» / `/api/user/analytics` | `services/accountInsights.ts → accountAnalytics()` — `TrafficUsageBucket.findMany()` + `TrafficDomainStat.groupBy()` | нода |
| Бюджет инфраструктуры (только админам) | те же бакеты + egress-бюджет ноды | нода |
| Счётчики конкретной сессии в админке / CLI | `Session.bytesRx/bytesTx` | нода, а для браузерного режима — наш локальный proxy |

Ключевой момент: **квота и аналитика никогда не читали клиентские числа.**
Они всегда агрегировались из `TrafficUsageBucket`, который заполняет только
доверенный отчёт ноды (`control-server/src/routes/node.ts`, схема пира —
только счётчики байт, без URL, без payload, без DPI). Обновление счётчиков
сессии в отчёте ноды идёт «только вперёд»:
`bytesRx > session.bytesRx ? bytesRx : session.bytesRx`, то есть отчёт не может
обнулить или уменьшить расход.

## 3. Что было уязвимо и что изменилось

До изменения `POST /api/vpn/stats` и `POST /api/vpn/disconnect` принимали
`uploadBytes` / `downloadBytes` (`bytesRx` / `bytesTx`) от любого
аутентифицированного клиента и поднимали ими `Session.bytesRx/bytesTx`
через `Math.max`. Подделать расход тарифа было нельзя (квота считается
из бакетов), но можно было «раздуть» цифры в админской выдаче по сессиям.

Теперь в `control-server/src/routes/vpn.ts` есть проверка репортера:

```ts
function isTrustedTrafficReporter(request: FastifyRequest): boolean {
	const ip = clientIp(request)
	return ip === "127.0.0.1" || ip === "::1" || ip === "::ffff:127.0.0.1"
}
```

* доверенный репортер (наш `glukvpn-browser-proxy`, который ходит на
  `http://127.0.0.1:8081` / `:8082`) — байты принимаются;
* любой внешний вызов — поля байт молча игнорируются, сессия обновляется
  только как признак «я ещё жив»;
* ответ `/api/vpn/stats` теперь содержит `countersAccepted: boolean`, чтобы
  было видно, учли счётчики или нет (поле additive, старые клиенты не ломаются).

Клиенты приведены в соответствие:

* расширение (`extension/lib/api.js`, `extension/background.js`) больше не
  отправляет байты — только `{ sessionId, transport: 'browser' }`;
* Flutter (Android/Windows) `/api/vpn/stats` не вызывает вообще;
* сайт цифры только читает.

## 4. Остаточные риски (честно)

1. **Скрыть трафик можно только не пуская его в туннель.** Если пользователь
   качает мимо VPN — мы этого не видим и видеть не должны. Внутри туннеля
   считает нода, обойти это клиентом нельзя.
2. **Доверие построено на loopback-IP.** Поэтому нельзя менять поведение
   `clientIp()` (`request.ip`) и включать `trustProxy` так, чтобы
   `X-Forwarded-For` подменял `request.ip` — иначе внешний клиент сможет
   притвориться loopback. Наш proxy обязан продолжать обращаться к
   `127.0.0.1`, а не к публичному домену.
3. **Отказ по квоте пока текстовый.** Сообщение вида
   `Monthly traffic limit reached (5 GB)...` клиенты распознают по тексту.
   Это работает, но правильнее добавить машинный код ошибки
   (`code: "traffic_limit"`) — задача на будущее, клиентские подстройки уже есть.
4. **Ретеншн бакетов — 400 дней** (`services/monitor.ts`), дальше история
   не восстанавливается.

## 5. Как проверить руками

```bash
# 1. Обычный клиент пытается прислать 100 ГБ:
curl -X POST https://api.gluk.tech/api/vpn/stats \
  -H "authorization: Bearer <user-token>" -H "content-type: application/json" \
  -d '{"sessionId":"<id>","uploadBytes":107374182400}'
# Ожидаем: { "ok": true, "countersAccepted": false, ... } и НЕизменённые счётчики.

# 2. Квота не двинулась:
curl https://api.gluk.tech/api/vpn/status -H "authorization: Bearer <user-token>"
# quota.usedBytes должен остаться прежним.
```

## 6. Правило на будущее

Любая новая площадка показывает расход **только** из ответов
`/api/vpn/status` → `quota` и `/api/user/analytics`. Локальные счётчики
(WireGuard handshake, sing-box stats, chrome.webRequest) допустимы
исключительно как «скорость сейчас» в реальном времени и никогда — как
источник расхода тарифа.
