Четыре жалобы из этого раунда, и все четыре оказались не косметикой.

## 1. «Приложение не установлено» при обновлении

Диагноз из ТЗ верен полностью: дело в подписи, а не в Android.

В `.github/workflows/build-apk.yml` подпись релизным хранилищем стоит под
условием `if: env.HAS_KEYSTORE == 'true'`, где `HAS_KEYSTORE` — это проверка
секрета `ANDROID_KEYSTORE_BASE64`. Секрета нет, поэтому каждая сборка уходила
по второй ветке: `flutter build apk --release` без `signingConfig` подписывает
APK **отладочным** ключом, а отладочный ключ создаётся на машине при первой
сборке. Раннер GitHub каждый раз новый — значит и ключ каждый раз новый.

Android не заменяет установленное приложение сборкой с другой подписью: это
базовая защита, иначе любой APK мог бы подменить ваш банковский клиент. Отсюда
и «Приложение не установлено», и необходимость удалять приложение с данными.

Вторая половина проблемы — `versionCode`. Он брался из `pubspec.yaml` (`+2`) и
не менялся между сборками, а Android сравнивает его раньше всего: равный код
делает установку молчаливой заменой, меньший — отклоняется. Отсюда «оставляет
старую версию в системе без предупреждения».

**Что изменено в CI**

* `--build-number="$GITHUB_RUN_NUMBER"` — `versionCode` растёт на каждой сборке.
* Ветка без ключа больше не делает вид, что всё хорошо: артефакт называется
  `glukvpn-DEBUGKEY-do-not-distribute.apk`, в лог печатается `::error::`, а шаг
  публикации в Releases пропускается (`if: env.HAS_KEYSTORE == 'true'`). Раньше
  неустанавливаемый APK спокойно уезжал в релизы.
* Починен `grep '^version:' pubspec.yaml`: шаги и так стартуют в
  `flutter-client`, поэтому старый путь `flutter-client/pubspec.yaml` не
  находил ничего и тег выходил как `android-v-build57`.

**Что нужно сделать один раз руками** (я не могу создать хранилище ключей за
вас — это бинарник, и он не должен попадать в репозиторий):

```powershell
keytool -genkeypair -v -keystore glukvpn-release.jks -alias glukvpn `
    -keyalg RSA -keysize 4096 -validity 10000

# в буфер обмена — это и есть значение секрета
[Convert]::ToBase64String([IO.File]::ReadAllBytes("glukvpn-release.jks")) | Set-Clipboard
```

Затем в Settings → Secrets and variables → Actions добавить четыре секрета:
`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`
(`glukvpn`), `ANDROID_KEY_PASSWORD`.

Два честных предупреждения:

1. **Первое обновление всё равно придётся поставить через удаление.** На
   телефонах сейчас стоит сборка с отладочным ключом; перейти с неё на
   нормальную подпись поверх невозможно по той же причине, что и раньше. Это
   последний раз.
2. **Файл `.jks` нельзя терять.** Потеря ключа = ещё одна такая же миграция
   для всех пользователей. Резервная копия вне репозитория, `*.jks` в
   `.gitignore` не просто так.

## 2. Пять кликов по версии в расширении

Жалоба справедлива, и причина неприятная: в раунде 11 жест был удалён на
телефоне и на ПК, а в расширении — нет, потому что папка
`glukvpn-extension-1.5.0/` лежала в `.gitignore` (строка 70). Поиск по
репозиторию её не видел, поэтому «удалено везде» было неправдой. Игнор снят в
раунде 11.5, и то же самое всплыло с дублирующим баннером.

Удалено в `extension/ui/popup.js`: `devUnlocked`, `versionTaps`,
`versionFirstTap`, вся функция `onVersionTap()` и её обработчик на
`#btn-version`. В `popup.html` кнопка версии стала `<span>` — кнопка, которая
ничего не делает, продолжает приглашать нажать.

Видимость теперь считается одним выражением: `const channelVisible = isAdmin`.
Вместе с переключателем канала под админа спрятан и блок разработчика
(`btn-devmode` / `dev-body`) — там правка адреса Control API и адреса сайта.
Спрятать переключатель и оставить рядом поле «Control API» значило бы сдвинуть
граблю на строку вниз: обычный пользователь получает клиент, который никуда не
стучится, и никак не может связать это со своими действиями.

Почему не «секретный жест для тестировщика»: жест — это не право. Он позволял
обычному аккаунту открыть переключатель, который бета-плоскость всё равно
отвергнет, а администратору — требовал знать фокус, чтобы дойти до штатной
возможности.

## 3. «Всё должно быть на проде, а переключатель — внутри»

Три разных причины, по одной на клиент.

**Телефон — почему нельзя было войти.** `ChannelController.restore()`
восстанавливает канал из хранилища **до** того, как известно, кто именно
вошёл. Устройство, когда-то переключённое на бету, продолжало обращаться к
бета-плоскости; это отдельный деплой с отдельной базой, аккаунта там просто
нет. А раунд 11 спрятал переключатель от не-админов — и убрал единственный
путь назад. Симптом ровно тот, что описан: «пароль перестал работать».

Появился `ChannelController.demoteIfNotAdmin(user)`; `main.dart` на
бета-пути один раз поднимает сессию и, если она не админская (или её нет
вовсе), возвращает клиент на PROD до первого кадра. Метод идемпотентен: на
PROD он выходит сразу, поэтому `switchTo` → `bootstrap` не может закольцеваться.

**Телефон — почему сборка вообще уезжала на бету.** В воркфлоу
`API_BASE_URL` подменялся на `beta-api.gluk.tech` для ветки `beta`, а
`ALLOW_BETA_CHANNEL` выставлялся `true` только там же. То есть публичная
сборка шла с **выключенной** бетой (переключателя нет даже у админа), а
бета-сборка — с зашитым бета-адресом (войти не может никто, кроме админа).
Теперь шаг сборки принудительно возвращает прод-адрес, если ему подсунули
бета-хост, и всегда компилирует бету внутрь: `--dart-define=ALLOW_BETA_CHANNEL=true`.

**ПК — почему переключателя «нету».** `desktop/packaging/build-all.ps1`
добавлял `--dart-define=ALLOW_BETA_CHANNEL=false` для всех публичных сборок.
При этом `dev_channel_switch.dart` рисует переключатель по `isAdmin`, а
`AppConfig.setChannelOverride(beta)` в такой сборке возвращает `false` —
переключатель есть, нажатие не делает ничего и ничего не объясняет. Строка
убрана: кому показывать переключатель, решает админ-гейт
(`ChannelController.canSwitchAs`), а не компилятор.

Итог по всем клиентам: адрес по умолчанию — прод; бета существует в сборке;
видит её только администратор; не-админ, доставшийся с бетой из прошлой
сборки, молча возвращается на прод.

## 4. «Сеть осталась GlukVPN 11»

Wintun удаляет адаптер, когда воркер закрывает его штатно. Падение, `kill` или
выключение питания оставляют устройство зарегистрированным, а Windows не
переиспользует занятое дружественное имя — отсюда `GlukVPN 2`, `GlukVPN 3` и
далее до одиннадцати.

Это не только косметика, и поэтому пункт связан с «на ПК не работает
интернет»: каждый призрак сохраняет свои маршруты и регистрацию в DNS, и
резолвер может продолжать отдавать трафик интерфейсу, который уже ничего не
пересылает.

В `native/glukvpn-tunnel-service/src/tunnel.cpp` добавлена
`PurgeGhostAdapters()`, вызывается из `WorkerMain` **до** запуска воркера. Два
сознательных решения:

* удаляются только устройства со статусом не `OK`, поэтому адаптер живой
  сессии снести невозможно;
* чистка синхронная и строго до создания нового адаптера — параллельная
  чистка могла бы удалить новое устройство, пока оно поднимается. Ожидание
  ограничено 20 секундами, туннель поднимается независимо от результата.

Внутри — `pnputil` через PowerShell: перечисление класса Net из C++ означало
бы тащить SetupAPI ради задачи, которая выполняется раз на подключение. Если в
вашей среде PowerShell для служб заблокирован политикой, это место придётся
переписать на SetupAPI — в логе будет `Ghost adapter sweep could not start`.

Ручной эквивалент (от администратора):

```powershell
Get-PnpDevice -Class Net -FriendlyName 'GlukVPN*' |
    Where-Object Status -ne 'OK' |
    ForEach-Object { pnputil /remove-device $_.InstanceId }
```

## Что осталось

* **«На ПК не работает интернет».** Нужен `tunnel-worker.log` — там теперь
  строка `adapter: name=... luid=...`, по ней видно, совпадает ли адаптер, на
  который ставятся маршруты, с тем, что создал воркер. Чистка призраков
  снимает одну из версий, но подтвердить её без лога нельзя.
* **Единый экран профиля** на телефоне и ПК: данные аккаунта, подписка и
  секция «Безопасность» (смена пароля, привязка Telegram). Пока привязать
  Telegram можно только в личном кабинете на сайте — именно туда и отправляет
  бот, когда отвечает «Этот Telegram не привязан ни к одному аккаунту».
* **`linkAuth.ts`** — коды быстрого входа живут в памяти процесса; перезапуск
  сервера роняет живые коды в 404.
* **Страницы `/en/`** — трёхтабный вход, `.sec-actions`, локализация ошибок.
* **RAS-профиль** для Quick Settings Windows 11 (с оговорками из раунда 11).
