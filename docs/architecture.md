# Архитектура

## 1. Главный принцип: control plane ≠ data plane

Система разделена на две независимые плоскости.

**Control plane** (`control-server`) решает, *кому разрешено*: аутентификация,
устройства, подписки, реестр нод, выдача и отзыв доступа, учёт, аудит.
Работает только по HTTPS, слушает `127.0.0.1:8081` за nginx aaPanel.

**Data plane** (`node-agent` + ядерный WireGuard) передаёт трафик. Агент — это
только исполнитель команд и сборщик метрик; сам трафик шифрует и маршрутизирует
ядро Linux, а не наш код.

Следствия, которые важны на практике:

- API не слушает UDP и в принципе не содержит кода пересылки пакетов —
  проксировать VPN-трафик ему нечем;
- падение control plane не рвёт уже установленный туннель: peer уже в ядре,
  трафик идёт. Перестанут работать только новые connect/disconnect;
- ключи туннеля никогда не сходятся в одной точке: приватный ключ клиента — на
  телефоне, приватный ключ ноды — на ноде, в БД — только публичные.

Границы доверия: агент не имеет доступа к PostgreSQL и не знает о
пользователях ничего — только публичные ключи и IP; клиент не знает ничего о
других пользователях и не может выбрать себе IP или чужой ключ.

## 3. Поток подключения

```
телефон                 control plane                 нода
   │ login                     │                            │
   │──────────────────────▶│ Argon2id, JWT 15мин          │
   │◀──── access + refresh ────│                            │
   │                           │                            │
   │ генерация X25519         │                            │
   │ (приватный остаётся)    │                            │
   │ register device (pubkey)  │                            │
   │──────────────────────▶│ лимит 3 устройства          │
   │                           │                            │
   │ POST /api/vpn/connect     │                            │
   │──────────────────────▶│ проверки: user ACTIVE,      │
   │                           │ device ACTIVE, подписка,    │
   │                           │ лимит сессий, нода ONLINE  │
   │                           │ аренда IP из 10.8.0.0/24    │
   │                           │ ADD_PEER в очередь         │
   │                           │◀──── heartbeat (10с) ───────│
   │                           │──── commands[] ──────────▶│ wg set peer
   │                           │◀──── ack DONE ───────────│
   │◀─ tunnel config (201) ────│                            │
   │   endpoint, node pubkey,  │                            │
   │   свой IP, DNS, MTU       │                            │
   │                                                        │
   │  WireGuard handshake, UDP 51820                         │
   │─────────────────────────────────────────────▶│──▶ NAT → Internet
```

Клиент ожидает флаг `peerReady` в `/api/vpn/status` (опрос каждые 3 секунды,
watchdog 20 секунд) и только после этого поднимает туннель — иначе первые
пакеты ушли бы в никуда, пока агент не забрал команду.

Отключение — зеркально: клиент гасит туннель локально, затем `disconnect`,
control plane ставит `REMOVE_PEER`, освобождает аренду IP и закрывает сессию с
итоговыми байтами.

## 4. Почему heartbeat — это канал команд

Отдельного `GET /api/node/commands` нет намеренно. Ответ на heartbeat сам несёт
`commands[]`. Плюсы: одно соединение вместо двух, нет входящих подключений на
ноду (не нужен ни один лишний открытый порт), нет отдельного endpoint'а,
который можно забыть защитить. Клиентская латентность решается тем, что агент
опрашивает очередь чаще (3 секунды), чем отправляет полный heartbeat.

Состояния команды: `PENDING → DELIVERED → DONE | FAILED`. Зависшие в `DELIVERED`
возвращаются в очередь (`requeueStaleCommands`), поэтому рестарт агента посреди
команды не теряет её. `ADD_PEER`/`REMOVE_PEER` идемпотентны — `wg set` безопасно
повторять.

`POST /api/node/report` закрывает рассогласование состояний: нода присылает
фактический список peer'ов, а в ответ получает `removePeers[]` (лишние, которые
надо убрать) и `missingPeers[]` (должны быть, но их нет). Так система
самовосстанавливается после перезагрузки ноды или `wg-quick down`.

## 5. Аренда IP

Пул `10.8.0.0/24`, `10.8.0.1` — сама нода. Таблица `ip_leases` с уникальным
`[node_id, ip]` и уникальным `session_id`: два одновременных connect не могут
получить один IP даже при гонке — это гарантирует БД, а не приложение. Аренды
без живой сессии освобождаются через `LEASE_RECLAIM_AFTER_SEC = 300`.

## 6. Мониторинг и статусы ноды

`PENDING` → нода зарегистрирована, heartbeat ещё не пришёл.
`ONLINE` → heartbeat свежее 30 секунд. `OFFLINE` → просрочен.
`DISABLED` → выключена админом, новые подключения запрещены.

Статус вычисляется на чтении (`effectiveNodeStatus`), а не только пишется в БД —
зависший `ONLINE` при мёртвой ноде невозможен. Фоновый `monitor` (тик раз в
15 секунд) дополнительно: пишет `node.offline` в аудит, закрывает сессии нод,
молчавших 4×30 секунд, отключает сессии с истёкшей подпиской, возвращает в
очередь зависшие команды, чистит старые `login_attempts`.

При падении ноды: статус `OFFLINE`, `connectable = false`, клиент показывает её
неактивной и блокирует кнопку. Автопереключения на другой регион нет по
требованию.

## 7. Учёт трафика

Агент читает `wg show <iface> dump`: на peer'а есть rx/tx и время handshake.
Счётчики в ядре монотонно растут, поэтому control plane берёт максимум из
пришедшего и сохранённого значения: перезапуск `wg0` не открутит статистику
назад. Байты хранятся как `BigInt`.

Собирается только: сколько байт, когда началось, когда закончилось, какое
устройство, какая нода. Ни URL, ни DNS, ни содержимого.

## 8. Модель данных

```
users ───┬──▶ devices ───────┐
         ├──▶ subscriptions   │
         ├──▶ refresh_tokens  │
         └──▶ sessions ◀──────┘
                  │
vpn_nodes ─┬──▶ sessions
           ├──▶ ip_leases
           ├──▶ node_tokens
           ├──▶ node_enrollment_tokens
           └──▶ node_commands
audit_logs, login_attempts — без жёстких связей
```

Сверх минимума из техзадания добавлены четыре таблицы, без которых требования
не выполнимы: `refresh_tokens` (отдельные refresh-токены и revoke),
`node_tokens` + `node_enrollment_tokens` (свой credential на ноду, ротация,
expiration), `node_commands` (асинхронные add/remove peer), `ip_leases`
(атомарная выдача IP), `login_attempts` (троттлинг логинов).

Схема меняется только через Prisma-миграции (`prisma migrate deploy`).
Ручной SQL по базе — не санкционированный путь.

## 9. Масштабирование на DE-02 / US-01 / FR-01

Ничего переписывать не надо:

1. на control plane: `nodes:token` → одноразовый enrollment-токен;
2. на новой VM: WireGuard + агент + `npm run enroll`;
3. нода сама появляется в `GET /api/nodes` и в списке серверов приложения.

Каждая нода несёт свой `subnet_cidr`, `dns`, `mtu`, `capacity` и порт — глобальных
констант сети в коде нет. `listSelectableNodes()` уже возвращает множество нод и
сортирует их по загрузке, а `connect` без `nodeId` выбирает лучшую доступную.

## 10. Принятые решения и альтернативы

| Решение | Почему | Альтернатива |
| --- | --- | --- |
| Node.js + Fastify | один язык на API и агент, готовые плагины безопасности | FastAPI — тоже валидно, но два разных рантайма |
| Без Docker | aaPanel уже владеет nginx и портами; systemd проще и безопаснее для агента с CAP_NET_ADMIN | docker-compose добавил бы слой и риск конфликта с aaPanel |
| Без Redis | очередь команд — таблица, rate limit — в памяти одного процесса | Redis нужен только при нескольких инстансах API |
| Ключи генерит клиент | приватный ключ физически не может утечь с сервера | генерация на сервере проще, но нарушает требование |
| Агент без доступа к БД | компрометация exit-узла не даёт данные сервиса | прямой доступ к Postgres — грубая ошибка |
| `wg set` вместо правки wg0.conf | не нужен рестарт интерфейса, не рвёт чужие сессии | редактирование конфига — гонки и обрывы |

## 11. Клиент: почему ключи клампятся

X25519-приватный ключ по RFC 7748 должен быть клампнут (`[0] &= 248`,
`[31] &= 127`, `[31] |= 64`). `wireguard-go` клампит ключ сам при загрузке, и если
публичный ключ был посчитан до клампинга, на ноде окажется чужой peer —
handshake молча не состоится. Клиент клампит до вывода публичного ключа,
`ensureDeviceRegistered` перегенерирует пару при несовпадении, а на этот
инвариант есть юнит-тест с векторами RFC 7748.
