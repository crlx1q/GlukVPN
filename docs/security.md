# Security — технические детали

Ответы на вопросы «где какой секрет», «какой трафик куда идёт» и «что при
компрометации» — в корневом `SECURITY.md`. Здесь — реализация: какие проверки
где стоят и что именно ломается, если убрать любую из них.

## 1. Цепочка проверок запроса

```
nginx (HTTPS, aaPanel)
  └─▶ fastify
       ├─ helmet            security headers
       ├─ cors              список из CORS_ALLOWED_ORIGINS, по умолчанию пусто
       ├─ rate-limit        120/мин на IP + поштучные лимиты
       ├─ zod               валидация тела/параметров до любой логики
       ├─ requireUser       подпись JWT, статус пользователя из БД
       ├─ requireDeviceScope deviceId в claims + устройство ACTIVE
       ├─ requireAdmin      флаг isAdmin из БД, не из токена
       └─ requireNode       node-токен + X-Node-Id, сравнение HMAC
```

Важные детали реализации:

- **статус берётся из БД, а не из токена.** Заблокированный пользователь или
  отозванное устройство получат 403 сразу, даже с валидным JWT. Поэтому
  ограничение «токен живёт до 15 минут» касается только случая, когда и аккаунт,
  и устройство остаются активны;
- **`requireDeviceScope` отделён от `requireUser`.** Только токен, выданный после
  регистрации устройства, может вызывать connect/disconnect — веб-сессия
  админки физически не может открыть туннель;
- **`requireAdmin` не верит claim'ам.** Флаг `isAdmin` всегда читается из таблицы
  `users`: подмена payload без `JWT_SECRET` невозможна, а с ним — уже не имеет
  значения;
- **сравнение токенов константное по времени** (`safeEqualHex`) — никаких `===`
  на секретах.

## 2. Валидация ввода

| Поле | Правило |
| --- | --- |
| `username` | 3–64 символа, trim |
| `password` | 8–256 символов |
| `publicKey` | `^[A-Za-z0-9+/]{43}=$` и ровно 32 байта после декодирования |
| `refreshToken` | 20–512 символов |
| `nodeId`, `deviceId`, `sessionId` | UUID, плюс проверка принадлежности вызывающему |
| сетевые поля ноды | CIDR /16–/30, порт 1–65535, MTU 1280–1500 |

Проверка принадлежности есть везде, где есть `:id`: чужой `device_id` даёт 404,
а не 403 — чтобы не подтверждать существование объекта.

`assertDistinctKeys` не даёт зарегистрировать устройство с публичным ключом,
равным ключу ноды: иначе `wg set` мог бы сломать интерфейс.

## 3. Почему нет шелл-канала

Агент принимает только `ADD_PEER`, `REMOVE_PEER`, `SYNC_PEERS`. Внутри агента
нет ни `exec`, ни `shell: true`, ни склейки строк в команду: вызов `wg` идёт
массивом аргументов, а публичный ключ сначала проверяется регуляркой.
Даже полностью скомпрометированный control plane не может через этот канал
выполнить произвольную команду на ноде — только добавить/убрать peer.

## 4. Права процессов

**control-api** (`vpn-control.service`): пользователь `vpncontrol`, пустые
`CapabilityBoundingSet` и `AmbientCapabilities`, `NoNewPrivileges`,
`ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`,
`ProtectKernelTunables/Modules/Logs`, `RestrictAddressFamilies=AF_INET AF_INET6
AF_UNIX`, `SystemCallFilter=@system-service`, `UMask=0077`. Процессу не нужно
ничего, кроме сокета к Postgres и одного loopback-порта.

**node-agent** (`vpn-node-agent.service`): пользователь `vpnagent`, ровно
`CAP_NET_ADMIN` — без него `wg set` невозможен. Ни sudo, ни root, ни доступа к
БД, ни записи вне своего каталога.

Приватный ключ ноды (`/etc/wireguard/node.key`, root 0600) агенту не нужен и
недоступен: ключ загружает `wg-quick` при старте интерфейса, агент читает
только публичный ключ через `wg show`.

## 5. Сетевая поверхность атаки

| Слушает | Кто достучится | Зачем |
| --- | --- | --- |
| `443/tcp` | всей сети | API и админка через nginx |
| `51820/udp` | всей сети | WireGuard |
| `8081/tcp` | только loopback | API за прокси |
| `5432/tcp` | только loopback | PostgreSQL |

WireGuard молчит в ответ на пакеты без верного криптоключа — порт 51820 не
отвечает на сканирование и не выдаёт своё наличие.

Правила NAT привязаны к `-s 10.8.0.0/24`, а FORWARD — к паре интерфейсов
`wg0 ↔ <EGRESS_IF>`. Открытого ретранслятора из ноды не возникает.

## 6. Тесты безопасности (чек-лист)

Каждый пункт проверяется после развёртывания (см. `docs/deployment.md`,

| Проверка | Ожидание |
| --- | --- |
| запрос без токена | 401 |
| испорченная подпись JWT | 401 |
| истёкший access-токен | 401 |
| refresh-токен повторно | 401 |

## 7. Чего в коде нет намеренно

Нет обхода блокировок, обфускации трафика и маскировки под другие протоколы.
Нет скрытого прокси и автозапуска без явного `systemctl enable`. Нет сбора
телеметрии с устройства и отправки данных третьим сторонам. Единственный
внешний вызов клиента — `api.ipify.org` для показа своего же exit-IP; его можно
убрать в `AppConfig`.

Андроид-клиент не пытается скрыть VPN: используется штатный `VpnService`,
системный диалог разрешения показывается явно, иконка ключа в статус-баре
остаётся видимой.

## 8. Приватность данных

В БД есть: username, хеш пароля, имена устройств, публичные ключи, времена
сессий, байты, IP внутри туннеля, IP-адреса обращений к API в аудите,
приблизительная страна и регион по IP последнего входа и доменная
статистика (только имя хоста из SNI/Host с байтами; строки удаляются
через `DOMAIN_STATS_RETENTION_DAYS`).
В БД нет: URL и путей, DNS-запросов, содержимого трафика, координат,
идентификаторов устройства (IMEI, Android ID) и приватных ключей.

Аудит чистить можно вручную (`DELETE FROM audit_logs WHERE created_at < ...`),
автоматического retention в прототипе нет.

## 9. Удаление аккаунта

Удаление сделано надгробием: строка в `users` не удаляется никогда. Она
остаётся со статусом `DELETED`, датой, причиной и тем, кто удалил, — плюс
`username` и хеш пароля. Всё остальное личное стирается в том же вызове:
почта, Telegram-профиль, страна и регион по IP, устройства, туннели,
refresh-токены, доменная статистика, счётчики трафика, коды и ссылки для
входа. Флаги `isAdmin`, `isTester` и ручной лимит скорости сбрасываются:
привилегии не должны переживать аккаунт.

Почему логин и хеш пароля остаются: `/api/auth/login` проверяет пароль
раньше статуса. Без них владелец удалённого аккаунта получал бы
«invalid username or password» и продолжал попытки, а с ними получает
чёткий `account_deleted`. Та же последовательность не даёт постороннему
выяснять, какие имена когда-либо существовали: с неверным паролем до
проверки статуса дело не доходит.

Почему строка остаётся вообще: публичный номер аккаунта не должен
достаться другому человеку, записям аудита нужно на кого-то ссылаться,
а поддержке — отвечать, что случилось с этим номером. История платежей
(заказы, подписки, использованные промокоды) тоже остаётся намеренно:
после стирания личных полей она ничего о человеке не говорит, зато это
единственная запись о прошедших деньгах.

Сначала закрываются туннели (`user_deleted`) и только потом удаляются
устройства: именно закрытие сессии ставит ноде `REMOVE_PEER`, а peer
без строки в БД остался бы на шлюзе. Синхронизация политики снимает
VLESS-доступ со всех нод (в политике есть только устройства `ACTIVE`
пользователей). Операция идемпотентна — повторный вызов ничего не
меняет и отвечает `alreadyDeleted: true`.

Кто может удалять: владелец — `DELETE /api/account` с текущим паролем
(3 попытки в час), администратор — `DELETE /api/admin/users/:id`. Себя админ
удалить не может, другого админа — только после снятия флага: админская
строка — ключ к сервису, и потерять последнюю одним нажатием нельзя.
В аудит пишутся `admin.user.delete`, `account.delete` и
`account.delete.rejected` (неверный пароль при самоудалении).

Политика целиком и причины каждого решения — в
`control-server/src/services/accountDeletion.ts`; коды отказа для клиентов — в
`docs/api.md`, раздел «Коды отказа аккаунта».
